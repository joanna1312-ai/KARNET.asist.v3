# 📊 Raport z Audytu Kodu — KARNET.asist (v3/app)

> Audyt przeprowadzony 2026-08-20 na gałęzi `main` (`app/`, Next.js 15 + Prisma 7 + NextAuth). Zakres: bezpieczeństwo i walidacja, typowanie, architektura, obsługa błędów, wydajność/czystość kodu, testy i konfiguracja. Audyt czysto analityczny — bez zmian w kodzie.

## 1. Podsumowanie Stanu Projektu

**Ocena ogólna: 7.5/10**

Kod jest zaskakująco dojrzały jak na projekt tej skali: autoryzacja własności zasobów (karnet/wizyta/plik vouchera) jest **konsekwentnie** egzekwowana w każdym z 20 route handlerów przez wspólny wzorzec `getCallerIdentity` → `findOwnedCard`/`ownerFilter`, `strict: true` w TS jest realnie przestrzegane (zero `any` poza wygenerowanym kodem Prisma), brak surowego SQL, brak `dangerouslySetInnerHTML` na danych użytkownika, a pokrycie testami logiki serwerowej i API jest solidne (28 plików testów jednostkowych + 17 testów route'ów API + 5 scenariuszy e2e w Playwright). Sekrety nie wyciekają do repo (`.env*` poprawnie w `.gitignore`, tylko `.env.example` jest trackowane) ani do frontendu (klucze bez `NEXT_PUBLIC_` faktycznie używane tylko server-side).

**Najmocniejsze strony:**
- Spójny, dobrze udokumentowany model autoryzacji (ADR-007: token urządzenia + sesja NextAuth, rozłączne przestrzenie danych) egzekwowany identycznie we wszystkich endpointach.
- Wysoka jakość walidacji wejścia (ręczne parsery typu `unknown → typed`, konsekwentnie, bez `as any`).
- Dobre pokrycie testami logiki biznesowej i API.

**3 główne punkty ryzyka:**
1. **Brak granic błędów i stanów ładowania na poziomie route'ów** (`error.tsx`, `loading.tsx`, `not-found.tsx` nie istnieją nigdzie w `src/app`) — aplikacja produkcyjna z realnym ruchem nie ma żadnego fallbacku na nieobsłużony wyjątek renderowania.
2. **Brak jakiegokolwiek rate-limitingu** — dotyczy to zarówno logowania/rejestracji (brute-force), jak i endpointu doradcy AI, który uderza w płatne API (Groq, Google Places).
3. **Brak nagłówków bezpieczeństwa** (CSP, X-Frame-Options, HSTS) — `next.config.ts` nie definiuje `headers()`, nie ma też `middleware.ts`.

## 2. Zidentyfikowane Problemy (Priorytetyzowane)

### [ŚREDNI] Brak rate-limitingu na logowaniu, rejestracji i doradcy AI
- **Lokalizacja:** `src/server/auth.ts` (CredentialsProvider), `src/app/api/auth/register/route.ts`, `src/app/api/ai/recommendations/route.ts`
- **Opis:** Endpoint logowania hasłem (`authorize`) i rejestracji nie mają żadnego throttlingu — atakujący może próbować bruteforce'ować hasła lub zalewać bazę kontami testowymi. `POST /api/ai/recommendations` wymaga tylko tożsamości urządzenia (którą każdy klient może sobie sam wygenerować przez `/api/device/register` bez żadnej weryfikacji człowieka), a każde wywołanie z nowymi/rzadkimi współrzędnymi triggeruje płatne zapytanie do Groq (odpowiedź Groq celowo NIE jest cache'owana — komentarz w kodzie) i potencjalnie do Google Places. To otwiera drogę do generowania kosztów (billing abuse), nie tylko klasycznego DoS.
- **Rozwiązanie:** Dodać rate-limiting per IP/per identity (np. `@upstash/ratelimit` + Redis/Vercel KV, albo prosty licznik w Postgresie) na `/api/auth/*` i `/api/ai/recommendations`. Dla AI — rozważyć też dzienny limit zapytań per urządzenie/konto.

### [ŚREDNI] Brak React Error Boundaries i stanów ładowania na poziomie route'ów
- **Lokalizacja:** cały `src/app/*` — brak `error.tsx`, `global-error.tsx`, `not-found.tsx`, `loading.tsx`
- **Opis:** Next.js App Router konwencjonalnie oczekuje tych plików do przechwytywania błędów renderowania i pokazywania stanu ładowania podczas nawigacji/Suspense. Ich brak oznacza, że nieprzechwycony wyjątek w dowolnym komponencie (np. `undefined` przy błędnym kształcie odpowiedzi API) wywala całą stronę na domyślny, niestylowany ekran błędu Next.js — zły UX w aplikacji produkcyjnej z realnymi użytkownikami (live od 2026-08-09).
- **Rozwiązanie:**
```tsx
// src/app/error.tsx
"use client";
export default function Error({ reset }: { error: Error; reset: () => void }) {
  return <ErrorFallback onRetry={reset} />;
}
```
Dodać także `global-error.tsx` (dla błędów w samym layoucie) i `not-found.tsx`.

### [ŚREDNI] Brak nagłówków bezpieczeństwa (CSP, X-Frame-Options, HSTS)
- **Lokalizacja:** `next.config.ts` (pusty `NextConfig`), brak `middleware.ts`
- **Opis:** Brak Content-Security-Policy, X-Content-Type-Options, X-Frame-Options i Strict-Transport-Security. Aplikacja obsługuje upload plików (voucherów) i renderuje treści z zewnętrznych źródeł (Google Maps/Places) — brak CSP zwiększa powierzchnię ataku w razie przyszłej podatności XSS, a brak X-Frame-Options dopuszcza clickjacking.
- **Rozwiązanie:** Dodać `headers()` w `next.config.ts`:
```ts
async headers() {
  return [{
    source: "/:path*",
    headers: [
      { key: "X-Content-Type-Options", value: "nosniff" },
      { key: "X-Frame-Options", value: "DENY" },
      { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains" },
    ],
  }];
}
```

### [ŚREDNI] Logika biznesowa (orkiestracja zapisu karnetu) wymieszana z komponentem UI
- **Lokalizacja:** `src/app/cards/page.tsx:215-340` (`handleFormSubmit`, 519 linii pliku)
- **Opis:** Komponent strony jednocześnie: buduje payloady API, orkiestruje wieloetapowy zapis (utwórz kategorię → utwórz firmę → utwórz/zaktualizuj karnet → wgraj/usuń pliki vouchera), zarządza ~12 stanami lokalnymi i renderuje UI. Ta logika nie jest pokryta żadnym testem jednostkowym/komponentowym (`find ./src/components -name "*.test.*"` → 0 wyników) — jedyne zabezpieczenie to e2e. Trudno to bezpiecznie refaktoryzować bez ryzyka regresji.
- **Rozwiązanie:** Wydzielić orkiestrację do custom hooka (np. `useCardFormSubmit`) lub modułu w `src/lib`, oddzielając fetch/logikę biznesową od JSX. Ułatwi to też pisanie testów jednostkowych bez renderowania całego drzewa komponentów.

### [ŚREDNI] Duplikacja wzorca walidacji zamiast wspólnej biblioteki (brak Zod mimo dużej liczby endpointów)
- **Lokalizacja:** `src/server/card-rules.ts`, `company-rules.ts`, `category-rules.ts`, `visit-rules.ts`, `auth-rules.ts`
- **Opis:** Każdy moduł powtarza ten sam schemat: `readX(value: unknown)` → `parseXInput(body)` → `getXInputErrors(candidate)` → w route handlerze `merged.field!` (non-null assertion po walidacji). Kod jest poprawny, ale to ręcznie utrzymywana reimplementacja tego, co daje schema-validation library. Rozjazd między `parseXInput` a `getXInputErrors` (np. ktoś doda pole w jednym, zapomni w drugim) nie jest wykrywany statycznie przez TS — asercje `!` maskują błąd aż do runtime.
- **Rozwiązanie:** Rozważyć migrację do `zod` (`z.object({...}).safeParse(body)`) — jeden schemat = walidacja + typ, eliminuje `!` i klasę błędów "zapomniałem dodać pole do walidacji".

### [NISKI] Brak weryfikacji własności rekordu `PushSubscription` po `endpoint`
- **Lokalizacja:** `src/app/api/push/subscribe/route.ts:32-49` (POST upsert) i linia 56-76 (DELETE)
- **Opis:** `POST` robi `upsert` po samym `endpoint`, bez sprawdzenia, czy istniejący wiersz już należy do innej tożsamości — jeśli endpoint się powtórzy, `update` nadpisze `userId`/`deviceId` bez porównania z wywołującym. `DELETE` usuwa `deleteMany({ where: { endpoint } })` bez żadnego filtra po identity. Realna eksploatowalność jest niska (endpoint to długi, losowy URL nadawany przez przeglądarkę/push service), ale to luka w defense-in-depth.
- **Rozwiązanie:** Dołączyć `ownerFilter(identity)`-podobny warunek do `where` w obu operacjach, tak jak w `card-owner.ts`.

### [NISKI] Porównanie `CRON_SECRET` nie jest stałoczasowe
- **Lokalizacja:** `src/app/api/cron/reminders/route.ts:11`
- **Opis:** `authHeader !== \`Bearer ${process.env.CRON_SECRET}\`` — standardowe porównanie stringów w JS nie jest stałoczasowe, teoretycznie podatne na timing attack. Przy 32-bajtowym hex sekrecie ryzyko praktyczne jest minimalne, ale to tania poprawka.
- **Rozwiązanie:** Użyć `crypto.timingSafeEqual` (po zrównaniu długości buforów) zamiast `!==`.

### [NISKI] Sekwencyjne wysyłanie powiadomień push w cronie
- **Lokalizacja:** `src/server/push-sender.ts:51-77`
- **Opis:** Podwójna pętla `for...of` z `await` w środku dla każdej subskrypcji każdego karnetu — przy większej liczbie użytkowników czas wykonania rośnie liniowo i może uderzyć w limit czasu funkcji serverless (Vercel Cron/Functions).
- **Rozwiązanie:** Zrównoleglić przez `Promise.allSettled` z rozsądnym batchowaniem (np. `p-limit` z limitem współbieżności 10-20), żeby nie przeciążyć API dostawcy push.

### [NISKI] Brak testów komponentowych dla złożonej logiki formularzy
- **Lokalizacja:** `src/components/` (0 plików `*.test.*`)
- **Opis:** Cała weryfikacja UI opiera się wyłącznie na 5 scenariuszach e2e (Playwright) — brakuje szybszych testów jednostkowych/komponentowych (np. Vitest + Testing Library) dla logiki w `CardForm.tsx`/`cards/page.tsx`, co utrudnia szybkie iterowanie i lokalizowanie regresji.
- **Rozwiązanie:** Dodać `@testing-library/react` i pokryć testami przynajmniej `handleFormSubmit` (po wydzieleniu do hooka, patrz punkt wyżej).

### [NISKI] Brak wymuszenia lint/test/typecheck w CI
- **Lokalizacja:** `.github/workflows/` zawiera tylko `db-backup.yml` i `reminders.yml`
- **Opis:** Nie ma workflow uruchamiającego `npm run lint`, `npm test`, `tsc --noEmit` przy PR/push — regresje typów czy łamiące testy mogą trafić do `main` niezauważone przed `next build` na Vercelu (który sam catchuje część błędów, ale nie testy jednostkowe/e2e).
- **Rozwiązanie:** Dodać `.github/workflows/ci.yml` z krokami `install → lint → typecheck → test → build`.

## 3. Plan Działań Naprawczych

**Quick Wins (< 1 dzień, niskie ryzyko):**
1. Dodać `error.tsx`, `global-error.tsx`, `not-found.tsx` w `src/app`.
2. Dodać `headers()` z podstawowymi nagłówkami bezpieczeństwa w `next.config.ts`.
3. Zmienić porównanie `CRON_SECRET` na `crypto.timingSafeEqual`.
4. Dodać filtr identity do `POST`/`DELETE /api/push/subscribe`.
5. Dodać workflow CI (`lint` + `test` + `tsc --noEmit`) na PR.

**Zadania średnioterminowe (1-2 tygodnie):**
6. Wprowadzić rate-limiting (Vercel KV/Upstash) na `/api/auth/*` i `/api/ai/recommendations`.
7. Zrównoleglić wysyłkę push w `push-sender.ts` (`Promise.allSettled` + limit współbieżności).
8. Dodać `loading.tsx`/skeletony na poziomie route'ów zamiast ad hoc w każdym komponencie.

**Refaktoryzacja długoterminowa:**
9. Wydzielić orkiestrację zapisu karnetu z `cards/page.tsx` do dedykowanego hooka/serwisu i pokryć testami.
10. Rozważyć migrację ręcznych parserów walidacji (`card-rules.ts` i analogiczne) na `zod` — eliminuje duplikację i non-null assertions.
11. Dodać testy komponentowe (Testing Library) dla kluczowych formularzy jako uzupełnienie e2e.
